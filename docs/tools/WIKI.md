# End-User Wiki

> **Location**: `src/wiki/` (legacy tools) and `src/modules/<id>/wiki/` (modules)  
> **Route**: `/wiki` and `/wiki/<tool>/<page>`  
> **Status**: Implemented (placeholder pages only)

---

## 1. Overview

The wiki is the end-user help of the app. Every tool card on the home page has a "?" link that opens that tool's wiki. Pages are plain Markdown files kept next to the code they describe: a page is added or edited by committing a `.md` file, with no code change.

Each tool owns one directory. The directory name is the tool slug and each file inside is a page; the page slug is the file name without `.md`. `index.md` is the tool's landing page, which the "?" link opens.

| Tool kind | Wiki directory | Slug source |
|---|---|---|
| Legacy tool (`src/data/toolsData.ts`) | `src/wiki/<slug>/` | `wikiSlug` field of the tool card |
| Module (`src/modules/<id>/`) | `src/modules/<id>/wiki/` | module `id` |

The "?" link is rendered by `src/ui-kit/components/HomeCardFrame.tsx`, a wrapper that places the link beside the card (never inside the card's own link) so the two anchors do not nest.

Every wiki page shows a floating back-to-top button once the page is scrolled down; it is provided by `WikiShell`, so there is nothing to configure per tool.

## 2. Adding a Page to a Tool

Create a `.md` file in the tool's wiki directory:

```md
---
title: "Connecting to the database"
order: 2
---

# Connecting to the database

Page content here.
```

### Frontmatter fields

| Field | Required | Meaning |
|---|---|---|
| `title` | Yes | Name shown in the wiki navigation. A page without a title fails the test suite. |
| `order` | No | Integer used to sort pages within the tool (ascending). |

Only a leading `---` block with these two fields is understood; other keys are ignored.

### File names

A page file name may contain only lowercase letters, digits, hyphens and underscores, plus `.md` (for example `upload-step.md`). The file name becomes the URL, so `Guía de uso.md`, `A.md` or `a b.md` make the build fail with an error naming the tool and the file.

---

## 3. Giving a New Module a Wiki

Declare the directory in the module manifest (`src/modules/<id>/manifest.ts`):

```ts
wiki: { contentDir: "src/modules/<id>/wiki" },
```

Then add `src/modules/<id>/wiki/index.md`. The home card of the module must wrap its card in `HomeCardFrame` with the module slug and title.

## 4. Adding a Wiki to a Legacy Tool

1. Set `wikiSlug` on the tool in `src/data/toolsData.ts`.
2. Create `src/wiki/<slug>/index.md` (plus any other pages).

`ToolCard` already wraps every card in `HomeCardFrame`, so the "?" link appears automatically.

## 5. Markdown Features

### Callouts

A blockquote whose first line is a marker becomes a callout:

```md
> [!NOTE]
> Neutral information.

> [!TIP]
> A helpful suggestion.

> [!WARNING]
> Something that can cause data loss or an error.
```

### Links

Link to another page of the same tool with a relative `.md` path:

```md
See [the upload step](./upload.md).
```

### Images

Place the image next to the page and reference it with a relative path:

```md
![Upload screen](./upload-screen.png)
```

Assets are served from `/api/wiki/assets/<tool>/<file>`. Allowed image types: `png`, `jpg`, `jpeg`, `gif`, `webp`, `svg`. Every asset is served with `X-Content-Type-Options: nosniff`; SVG also gets `Content-Security-Policy: default-src 'none'; style-src 'unsafe-inline'`, so scripts in an SVG never run.

---

## 6. Validation

The test suite fails when:

- a relative `.md` link points to a page that does not exist,
- an image reference points to a file that does not exist or has a disallowed type,
- a page has no `title`.

Run `npm run test` after editing wiki content.

## 7. Regenerating screenshots

Wiki screenshots are generated by Playwright, not captured by hand.

```
npm run wiki:screenshots
```

- Config: `playwright.wiki.config.ts` (fixed 1280x900 viewport, Chromium only). Specs match `tests/e2e/wiki-screenshots/**/*.shots.ts`, so `npm run test:e2e` never runs them.
- Output: `src/wiki/<tool>/images/<name>.png`. Reference them from a page as `![alt](images/<name>.png)`. Module tools write inside their own folder (`src/modules/<tool>/wiki/images/`): `shot.ts` picks that folder automatically when `src/modules/<tool>/wiki` exists. The images are committed to git, so regenerate and commit them whenever the UI changes.
- Data is fully mocked (`mockBackend`, fictitious databases, tables and profiles): no database is needed. The command reuses a dev server already running on port 3000 or starts `npm run dev` itself.
- Adding a tool: copy `tests/e2e/wiki-screenshots/db-db-sync.shots.ts` (and its `.mocks.ts`) to `<tool>.shots.ts`, change the `TOOL` slug, URL and steps, and take every image with `takeShot` from `tests/e2e/wiki-screenshots/shot.ts`. Never put real hosts, users, tables or credentials in the mocks.
