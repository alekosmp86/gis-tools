# Routine jobs: "Carga de ejes de calles" (EJ-1 to EJ-28)

Related: LOAD_SLICE1 (EJL-1 to EJL-26, built), TWINS (ET), RENUMBERED (ER), SPLIT_MERGE_LOAD (EJS, partly built; refines EJ-13, EJ-19, EJ-21).

## Context

The street axes (ejes de vía de circulación) arrive in the staging table `bdj_carto.ide_ejesviacirculacion`, filled with the csv-db tool (Comparar, key `reftramo + localidad + departamento`; geometry in `geom` as MultiLineString/LineString 32721 from the CSV EWKB). This job moves them into the final `carto` tables incrementally. The table `bdj_carto.ide_ejevisualizador` is not used any more.

Facts read from preprod (not rules):
- `carto.road_section` key is `reftramo_ideuy` (also what `access_point.id_road_section` stores: 899,501 of 968,402 access points match by `reftramo`, 549 by `id`, about 68k match neither and are never touched; there is no foreign key); `id_circulation_way` stores the IDE `idcalle` (= `circulation_way.id_calle`); `id_road_section_type` maps 1:1 from `tipo_vialidad` (CALLE 4, CALLE INTERNA 20, PASAJE 10, PASAJE INTERNO 21, PEATONAL 11, Ruta 1, SENDERO 15, VIRTUAL 19); `id_font` maps from `fuente` with the fixed table of `bdj_carto.bdj_ejes` (ANC 8, CARGA_MASIVA 35, DESDE_TSUBASA 34, Google 33, IDE 1, INE 3, INTENDENCIA_DE_CANELONES 13, INTENDENCIA_DE_CERRO_LARGO 14, INTENDENCIA_DE_DURAZNO 16, INTENDENCIA_DE_FLORES 17, INTENDENCIA_DE_FLORIDA 18, INTENDENCIA_DE_MALDONADO 20, INTENDENCIA_DE_MONTEVIDEO 21, INTENDENCIA_DE_RIVERA 24, INTENDENCIA_DE_ROCHA 25, INTENDENCIA_DE_SALTO 26, INTENDENCIA_DE_SAN_JOSE 27, INTENDENCIA_DE_SORIANO 28, INTENDENCIA_DE_TACUAREMBÓ 29, MTOP 7, OSM 32, UTE 31).
- Every section has an `addresses_master` row with URN `cgeo:road_section:id:<road_section.id>`, `latitud` 0 and `longitud` 0. Nothing has a foreign key to `road_section`.
- `carto.access_point` has NO geometry. The point geometry is `carto.address.geometry`, joined by `carto.address.id = carto.access_point.id` (the join `v_address_build` and `mv_addresses_2_0` use for the map; SRID 32721). `bdj_carto` is staging only (the ejes, and the INE locality polygons for `cloc_iso`) and is never a source of access point data. Access points are never deleted.
- `cloc_iso` (used by `mv_road_section` and `mv_road_section2`) is a 7-character locality code or a 4-character department code for rural sections. Taking the INE locality polygon (`bdj_carto.ine_localidades_pg`, SRID 32721) with the longest intersection, and the department code otherwise, equals the visualizador's value in 98.0% of a 19,861-row sample.
- pgRouting 3.3.0 in preprod: `pgr_createTopology` accepts `rows_where` and reuses existing vertices.
- The views `bdj_ejes`, `mv_road_section`, `mv_road_section2` still read the visualizador; an admin must redefine them. Outside this job.

## Job and endpoints

- EJ-1: A job `ejes-calles`, title "Carga de ejes de calles", is its own card in Trabajos de rutina (after "Carga de padrones"), with a one-sentence description and its own wizard (same "Volver a la lista" behaviour as the other jobs).
- EJ-2: Endpoints `POST ejes-calles/start` and `GET ejes-calles/status` (in `module.routes.json`), following the other jobs: connection in the body, table roles, polled `jobId`, one running job per target, Spanish errors, the password never logged or returned.
- EJ-3: The request carries `dryRun`. `dryRun: true` runs the analysis (EJ-8 to EJ-12) and writes nothing. `dryRun: false` runs the real load (the former environment switch was removed, see EJL-16).

## Analysis (read-only, one transaction)

- EJ-8: Staging checks: rows, distinct `reftramo`, `reftramo` that repeat (groups and rows, informational only: identity is reftramo + locality + department, see EJL-15 of the LOAD_SLICE1 spec), `reftramo` that is not an integer, rows with NULL or empty geometry, rows with an unknown `tipo_vialidad` or `fuente`, rows with an empty `idcalle`, rows whose `nombre`, `localidad` or `departamento` contain U+FFFD (`chr(65533)`, damaged encoding). The last one blocks with "Hay N filas con caracteres dañados (�) en nombre, localidad o departamento. Corrija la codificación y vuelva a cargar." Any of these except the counts and the repeated `reftramo` is a blocker for the apply.
- EJ-9: Each staging section is matched to `road_section.reftramo_ideuy` and classified: NEW (not in `road_section`), UNCHANGED, ATTR (`nombre`, `idcalle`, type or font changed), GEOM (geometry differs beyond 4 decimals in degrees, as Comparar; two geometries whose Hausdorff distance is below `GEOMETRY_TOLERANCE_M`, 0.001 m, are the same: a coordinate rounded to the other side of the snap grid is not a change. On dev this removes the 54 false GEOM left once the invalid file geometries are skipped; the other 557 of the 611 were those invalid geometries compared with the real line) and both when both change. Identity of a staging copy is `reftramo + locality + department`; repeated `reftramo` follow the twin rules and EJL-6/EJL-7. Staging rows with invalid or collapsed geometry, or shorter than `MIN_SECTION_LENGTH_M` (1 m) unless their `reftramo` holds access points, are discarded (ET-18): they feed no rule, and `stg_keys` does not count their `reftramo` as present. One-to-one renumbered pairs (ER-1) are taken out before EJ-10.
- EJ-10: A `road_section` row that is not in staging is REMOVED. A REMOVED section whose length is covered at least 95% (within 3.5 m, `PIECE_COVER_TOLERANCE_M`) by NEW sections of the same `idcalle` is a SPLIT (one old, many new); NEW sections that together cover at least 95% of the length of several REMOVED sections of the same `idcalle` are a MERGE (many old, one new); a REMOVED section covered at least 95% by exactly one NEW piece (single copy) is a replacement: a split with one piece (SPLIT_MERGE EJS-17), so its points move to that piece; the remaining REMOVED are plain removals, and a plain removal with access points is held and not acceptable (EJS-18). Collapsed staging rows (length under `GEOMETRY_TOLERANCE_M`) are dropped before this detection (ET-18); on dev that changed one split into a merge (new `reftramo` 1024950 on `idcalle` 21083, old 935978 and 998882), the correct reading: the collapsed piece was not a real section. A NEW section of the same `idcalle` is a piece of a split, or a merge member, of a removed section when (A) it covers at least `COVERAGE_RATIO` (95%) of the old section (stubs included), OR (B) it covers more than `SPLIT_PIECE_MIN_COVER_M` (10 m) AND at least `PIECE_OWN_FRACTION` (35%) of its own length. A NEW section that only touches the end of a removed section overlaps it by a few metres and fails both: on dev the touching neighbours at a bend overlap 4-5 m (old 1001462 / new 1030829, 4.0 m of a 707 m section; old 1001823 / new 1030832, 5.0 m of a 71 m section), so 2 m was too short and 10 m is the margin. A replacement next to a continuing street is a plain removal plus NEW sections, not a split. The rule is one SQL fragment (`isPieceSql(covered, oldLength, newLength)`, `domain/pieceSql.ts`) for splits, merges, the merge-member sink and the split points; each call passes the new section length (`piece_len`). (Status, slice C, BUILT: the split detection is unchanged; the accepted splits are applied per EJS-3 to EJS-16 of `ROUTINE_JOBS_EJES_CALLES_SPLIT_MERGE_LOAD_SPEC.md`.) Geometric twin losers (ET-20 to ET-27 of `ROUTINE_JOBS_EJES_CALLES_TWINS_SPEC.md`, a complement of the locality twins) are excluded from NEW, REMOVED, split and merge candidates before this detection: they are not REMOVED here; a loser in carto is a separate removal offer with source kind `twin`.
- EJ-11: `cloc_iso` of every NEW and GEOM section is computed: the INE locality polygon with the longest intersection with the section, the department code (from `departamento`, via `mv_country_province.iso_code_dpto`) when none intersects. The report shows how many got a locality and how many only a department.
- EJ-12: The report shows the counts of EJ-8 to EJ-11 as cards, the lists (SPLIT, MERGE, plain removals, new streets, ATTR) as expandable tables with the `reftramo` involved, the number of `access_point` rows that each REMOVED section holds, the privilege information, and the banner "Análisis: no se modificó ninguna tabla." The summary strip cell "Calles nuevas" shows the number of new streets, equal to the row count of the "Calles nuevas" list; the section-level count (`newSections - renumbered`) stays in "Todos los indicadores" as "Nuevos".

## Apply (real run)

- EJ-13: The real run needs the password, the Revisar summary and the acceptance of the review lists of EJ-12 (SPLIT, MERGE, plain removals), each with "Aceptar" per row and "Aceptar todos", as the partial-match pairs of padrones. Only accepted removals, splits and merges are applied; the rest are skipped and reported. Splits, merges and removals are never automatic and splits are not the standard case. Geometric twin removals (ET-24) are accepted per row (`accepted.twinRemovals = [{ref}]`), never by a global flag; they are applied through the plain removal path (kind `twin`) and are skipped with `not_accepted`, `has_points` or `repeated_old_ref` otherwise.
  - Status (slices C and D, BUILT for splits): a split has "Aceptar" per row only when every one of its points has a destination, automatic or chosen by the user on "Revisar puntos" (EJS-6, slice D); a split with a review or no-geometry point still without a choice shows "Requiere revisión". The server applies an accepted split only when it passes the refusal checks of EJS-3 to EJS-16 (SPLIT_MERGE spec); otherwise it is held and reported.
  - Status (slice A, BUILT for merges and plain removals): `accepted` is `{ plainRemovals: [{ref}], merges: [{newRef}], splits? }`. Entries are deduplicated, capped at `ACCEPTED_KEYS_LIMIT` per list (refused above it, never truncated), an integer string each, and an unknown key or shape is a 400. A non-empty `splits` keeps the EJ-3 message until the split slice. An empty `accepted` is valid. "Aceptar todos" sends explicit per-row keys. Slice 1 applied none of them; see SPLIT_MERGE_LOAD EJS-1.
- EJ-14: The apply is one transaction that locks the destination tables (`road_section`, `circulation_way`, `addresses_master`, `access_point` and the vertices table, `SHARE ROW EXCLUSIVE`), and ends with `ANALYZE` on the changed tables (the vertices table when the topology step created or deleted vertices). A failed COMMIT is reported as outcome unknown, as in the other jobs. Before the first write the job writes a gzip revert SQL file like actualizar-padron, registered and shown in the result.
- EJ-15: `circulation_way`: new `(id_calle, name)` pairs are inserted with the type and font of the first section and a `short_name` built with the abbreviation rules (EJ-23). Existing rows are not changed.
- EJ-16: `road_section` NEW: inserted with `reftramo_ideuy`, `id_circulation_way` = `idcalle`, the mapped type and font, `geometry` as one `LineString` (`ST_LineMerge`; if it stays multi-part the row is a blocker), `distance` = `ST_Length` with two decimals as text, and `id_address_master` of the row created by EJ-17.
- EJ-17: For each NEW section an `addresses_master` row is inserted (`urn` = `cgeo:road_section:id:<road_section.id>`, `latitud` 0, `longitud` 0) and linked to it.
- EJ-18: ATTR and GEOM sections update only the changed columns; a GEOM change recomputes `distance` and clears `source` and `target` so the topology step (EJ-20) reassigns them.
- EJ-19: Accepted SPLIT and MERGE: the new sections are inserted as NEW; the `access_point` rows of each old section are reassigned (`id_road_section` = `reftramo` of the new section) to the new section nearest to the point (`ST_Distance` measured from `carto.address.geometry`, joined by `address.id = access_point.id`; `access_point` has no geometry; tie broken by the lower `reftramo`); ambiguous points and points without address geometry follow EJS-5 to EJS-8; then the old sections and their address masters are deleted. The result lists every reassigned point (old and new `reftramo`, distance). No row is deleted before its points are reassigned.
  - Status (slice A, BUILT for the merge half): an accepted merge inserts its new section as NEW, moves every point of its old `reftramo`s to the new one (`assertWritten` on the count), then deletes the old sections and masters under a NOT EXISTS guard that aborts the whole transaction. A merge is skipped with its reason when an old `reftramo` names more than one current section (`repeated_old_ref`), its new `reftramo` has no single kept copy (`not_single_copy`), an old section belongs to another accepted merge (`shared_old_ref`), or an old section has no `reftramo` (`no_reftramo`). The result lists the merges and their point counts, not each point.
  - Status (slice C, BUILT for the split half): an accepted split inserts its pieces as NEW, moves each of its points by `reftramo` to its piece (nearest piece, EJS-3 to EJS-5; one guarded UPDATE, `assertWritten` on the count), then deletes the old section and master under the same guards as a merge. A point with no address geometry, or closer than `AMBIGUOUS_POINT_GAP_M` to two pieces, is a review point and holds the split unless the accepted payload chooses its piece (EJS-6, EJS-7). A split is skipped with its reason per the SPLIT_MERGE spec. A group that is not applied is held as a whole: its new sections are not inserted, and it is reported once in skipped (EJL-12, decisions in SPLIT_MERGE_LOAD).
- EJ-20 (BUILT, slice B): Topology, the load step `TOPOLOGY` after `REMOVE` and before `ANALYZE` (Spanish label in `plannedSteps`).
  - Address geometry (slice C, EJS-2 of the SPLIT_MERGE spec): `carto.address` geometry must be SRID 32721 for the split points. Information in a dry run; in a real run a blocker only when `accepted.splits` is non-empty.
  - Preflight (real-run blocker with a Spanish message, information in a dry run): the real run reads `pgr_version()` and checks that `pgr_createTopology(text, float8, text, text, text, text, text, boolean)` exists and that the current user has `EXECUTE` on it (`has_function_privilege`). The vertices table must be `<schema of road_section>.<road_section>_vertices_pgr` (the name pgRouting creates and uses); its id and geometry columns must be named `id` and `the_geom` (pgRouting hardcodes them); the table, geometry, id, source and target names passed to pgRouting must be plain lower-case identifiers. Indexes are required before the load, found through `pg_index`, `pg_class`, `pg_am` on the resolved tables (names are not assumed): a valid btree index whose leading column is `id`, `source` and `target` of `road_section`, a GiST index on the `road_section` geometry and a GiST index on the vertices `the_geom`. A missing index is listed by name, because pgRouting would create it on the table and the revert does not drop it.
  - Before the writes, inside the transaction and before the revert file: `ej_topo_ids` holds the ids of the NEW sections (merge-inserted ones included, they are NEW too) and of the GEOM-changed sections; `ej_vertex_candidates` holds the distinct `source` and `target` of the sections this load deletes or GEOM-changes, read before any write.
  - Topology: `pgr_createTopology('<schema>.<road_section>', TOPOLOGY_TOLERANCE_M (0.1), <geometry>, <id>, 'source', 'target', rows_where := '<id> IN (SELECT id FROM pg_temp.ej_topo_ids)', clean := false)`, skipped when `ej_topo_ids` is empty. It reuses existing vertices and sets no other section.
  - Result: pgRouting answers `OK` or `FAIL` (it catches errors and does not raise them); any answer other than `OK` aborts the transaction with a Spanish message that points to the server NOTICE log. A `FAIL` can leave earlier updates and inserted vertices behind, which the rollback removes.
  - Assert: every section of `ej_topo_ids` holds a source and a target; otherwise the transaction aborts and nothing is committed.
  - Counts: `topologyAssigned` (sections of `ej_topo_ids` with source and target), `verticesCreated` (ids above the largest id read before the step), `verticesDeleted` (EJ-27). `ANALYZE` of the vertices table runs when either is above 0.
- EJ-21: Plain removals (a section with no replacement): an accepted section with no `access_point` rows is deleted together with its address master. A section that holds access points is never deleted (nor is any access point): it is skipped and reported with its `reftramo`, `idcalle` and number of access points, as padrones reports what it cannot change. A plain removal that the file still names (a discarded row with its `reftramo`, or a discarded row at its place, with no kept new section there) is kept, not removed (EJS-19, `keptByDiscardedCandidate`). Renumber, split and merge run first, on kept rows only, as before.
  - Shared master (slice A decision F2): a section's address master is deleted only when nothing else holds it: no other section outside this delete, no `carto.address` row (`ejes-address`, `id_address_master`) and no `carto.padron` row (`id_address_master`). The load computes that once per deleted section (`ej_del.master_deleted`); the expected count, the DELETE and the revert's re-insert of masters use that same set. A master another section still uses is kept, and the revert never re-inserts it.
  - Points by id (slice A decision D2): some `access_point.id_road_section` values hold the section's `road_section.id` instead of its `reftramo`. A section is NEVER deleted (plain removal or merge delete) while any access point's `id_road_section` equals its `reftramo` or its `road_section.id` (conservative: a false match only keeps the section). The points of a removed section count both kinds in the report ("Puntos de acceso"), so a section with id-linked points is "has points" (plain) or refused with `points_by_id` (merge). Only the `reftramo` matches move (merges and renumbers, as before); id-linked points are never moved.
  - Status (slice A, BUILT): the delete runs after the point moves and only for applied rows (`ej_plain_plan`, reason null); the delete statement repeats the no-points guard, and a count mismatch aborts the transaction. A removal whose `reftramo` names more than one current section is skipped (`repeated_old_ref`), and one without a `reftramo` (`no_reftramo`). A removal with points is skipped with reason `has_points`. Access points are only ever updated (`id_road_section`), never deleted.
- EJ-22: After the apply the result shows "Siguiente paso sugerido": an administrator must refresh `bdj_ejes` (while it exists), `mv_road_section`, `mv_road_section2` and `mv_addresses_2_0`, with the command text like padrones.
- EJ-23: The `short_name` abbreviation rules (taken from `CirculationWay22.sql`) are one constant list in the job, applied only to the new `circulation_way` rows.

The report opens at most one list by default, in this order: "Repetidos por localidad" when it has rows; otherwise the first list with rows in the order Divisiones y reemplazos, Unidos, Renumerados, Renumerados retenidos, Sin reemplazo, Geometría inválida, colapsada o menor de 1 m, Calles nuevas, Cambios de atributos. So "Renumerados retenidos" opens by default only when it has rows and none of the lists before it (twins, splits, merges, renumbered) has rows.
- EJ-27 (cleanup, BUILT slice B): Vertex cleanup after the topology step deletes only vertices in `ej_vertex_candidates` that no section holds as `source` or `target` after the load (`NOT EXISTS` over `road_section`). Vertices outside the candidates are never deleted, so pre-existing orphans unrelated to the load are untouched. The rows deleted equal the count of the same predicate taken just before the delete (aborts otherwise). The vertex table obeys `total_after = total_before + verticesCreated - verticesDeleted` (aborts otherwise). Both checks are consistency checks under the table lock, not independent guarantees: the expected count is the same predicate read just before the delete, and the total compares the counts the step itself read.
- EJ-28 (revert, BUILT slice B): The revert file is written and verified before the first write, so its vertex part is built from the candidates, not from what the topology will decide. Order of the statements in the file:
  1. `ej_rev_vertices_del`: the candidate vertices, full rows (`the_geom` included), re-inserted only when missing (`NOT EXISTS`), so the candidates the load kept are skipped.
  2. `ej_rev_masters`: deleted address masters, re-inserted.
  3. `ej_rev_restore`: deleted sections, re-inserted with their original ids and every column, `source` and `target` included.
  4. `ej_rev_sections`: UPDATE of the section columns of the ATTR, GEOM and renumbered sections to their old values, `source` and `target` of GEOM-changed rows included.
  5. `ej_rev_points`: `access_point.id_road_section` of the moved points back to the old `reftramo`.
  6. `ej_rev_inserts`: DELETE of the inserted sections (their topology goes with them), address masters and ways.
  7. `ej_rev_vertices_new`: `DELETE FROM` the vertices table `WHERE id >` the largest id read before the load and `NOT EXISTS` a section naming the vertex. Last, after no section names the created vertices.
  The file is valid only before any later topology rebuild: a later `pgr_createTopology` with `clean := true` renumbers the vertex ids, so the restored `source`/`target` values and the id-range delete would no longer match. Run the revert before any such rebuild.
