# Routine jobs: "Carga de ejes de calles", real load slice 1 (EJL-1 to EJL-26)

Scope: real load of NEW, ATTR, GEOM, twin and renumbered sections. Out of scope: topology (EJ-20), splits and merges (EJ-19), plain removals (EJ-21), UI wiring beyond the "Cargar ahora" buttons of EJ-24 (Revisar and Resultado, built). Builds on EJ-3, EJ-13 to EJ-18, EJ-22, EJ-23 of `ROUTINE_JOBS_EJES_CALLES_SKELETON_SPEC.md`.

Superseded for merges and plain removals by slice A (`ROUTINE_JOBS_EJES_CALLES_SPLIT_MERGE_LOAD_SPEC.md`): an accepted merge or plain removal is applied, the rest of EJL-12 holds (splits and every row not accepted are skipped and reported, never modified).

## Criteria

- EJL-1: `dryRun:false` is accepted only with the password, the Revisar summary of the same staging data (its counts and its staging fingerprint, EJL-20) and an `accepted` object (empty allowed). Otherwise 400 with a Spanish message. A body that asks for accepted splits, merges or removals keeps the EJ-3 message.
- EJL-2: The apply is one transaction. It takes `LOCK TABLE ... IN SHARE ROW EXCLUSIVE MODE` on `road_section`, `circulation_way`, `addresses_master` and `access_point` with a `lock_timeout`, and ends with `ANALYZE` on the changed tables. A failed COMMIT is reported as outcome unknown.
- EJL-3: Blockers (EJ-8) are recomputed inside the transaction; any blocker aborts before the backup. A geometry that stays multi-part after `ST_LineMerge` is a blocker.
- EJL-4: The gzip revert SQL is written, verified and registered before the first write. A failure rolls back and leaves no file registered (EJL-21). Revert restores old values of updated rows (including `reftramo_ideuy` and `access_point.id_road_section`) and deletes inserted ids.
- EJL-5: `circulation_way`: new `(id_calle, name)` pairs are inserted with type and font of the first section (lowest `reftramo`) and the `short_name` of EJ-23. Existing rows are untouched. Sequences are repaired first. The pairs come from every kept copy that is NEW or moved to another `idcalle` (EJL-18).
- EJL-6: Identity of a staging copy is `reftramo + locality + department`. Per `reftramo`, K = copies kept by the twin rules, E = existing `road_section` rows with that `reftramo_ideuy`.
- EJL-7: K = E: copies are paired with existing rows by `idcalle` + name, then by lowest id; ATTR and GEOM are compared per pair. K > E: E pairs updated and K-E sections inserted as NEW. K < E: the K pairs are updated; the E-K surplus rows are reported (`reftramo`, id, access point count) and never deleted. Copies of the same locality and department count as one copy. Known limitation, accepted: the pairing by `idcalle` and name, then lowest id, is not a geometric identity. Two stretches of one street with the same `reftramo` are paired by name and id order, so a copy can pair with a row of another stretch; the difference then shows as GEOM and is applied, never as a delete.
- EJL-8: NEW `road_section`: `id_circulation_way` = `idcalle`, mapped type and font, one `LineString`, `distance` = `ST_Length` with two decimals as text, `source` and `target` NULL. Each NEW section gets one `addresses_master` (`urn` = `cgeo:road_section:id:<id>`, `latitud` 0, `longitud` 0) linked through `id_address_master`. Masters created are therefore equal to the inserted sections.
- EJL-9: ATTR and GEOM update only the changed columns; GEOM recomputes `distance` and clears `source` and `target`.
- EJL-10: Renumbered sections (same `idcalle`, Hausdorff under `RENUMBER_HAUSDORFF_M`, and the uniqueness of EJL-17): the same transaction updates `road_section.reftramo_ideuy` to the new `reftramo` and `access_point.id_road_section` of the points of the old `reftramo` to the new one. The `road_section.id` never changes. The result lists the section and the number of points moved.
- EJL-11: `access_point` rows are never deleted. The only write on that table is the `id_road_section` update of EJL-10. `road_section_vertices_pgr` is not written. Points matching neither a `reftramo` nor an id are not touched.
- EJL-12: Sections absent from staging, splits, merges and plain removals are not modified; they are reported as skipped. Slice A (SPLIT_MERGE_LOAD): an applied merge or removal is no longer skipped, and a group is held as a whole: every split's pieces, and the new `reftramo`s of every merge that is not applied, are not inserted (no section, master or way is created for them) and the group is reported once in skipped, with its old and new refs and its reason (`not_accepted`, `split_pending`, or the refusal reason). Every held group's old sections stay untouched. The analysis leaves the same pieces out of its new-section counts and of the new streets, so the two agree. Held renumber pairs are counted neither as removed nor as new; a held split's old section stays counted as removed in the analysis KPIs and is listed as a split. A renumber candidate that EJL-17 refuses is held as a unit: its old section is neither removed nor modified, and its new section and every copy of its new `reftramo` are not inserted. The two refs are reported together as one skipped row of kind `renumber`, with the reason. A repeated old `reftramo` holds one row per section it names, all with the same pair, so the skipped list shows one row per distinct (old `reftramo`, new `reftramo`) pair and the counts (analysis `renumberSkipped`, load `renumber_skipped`) count distinct pairs. Held sections are counted neither as removed nor as new, in the analysis counts and in the load.
- EJL-13: The result has counts (inserted, updated, renumbered, renumber skipped, ways created, points moved; masters created equal inserted, EJL-8), the skipped and surplus lists, the backup, and the "Siguiente paso sugerido" text of EJ-22. The renumber skipped count is the load's own count of the distinct pairs of the held set (`ej_held` rows, EJL-23), shown as "Renumerados retenidos" in the result counts; it equals the analysis count `renumberSkipped` of the same transaction.
- EJL-14: A second run over the same staging changes nothing. The real run stays refused by the server until `EJES_CALLES_REAL_RUN_ENABLED=true` (EJL-16).
- EJL-15: A `reftramo` repeated across localities is not a blocker (EJ-8 no longer blocks on it). Identity is reftramo + locality + department; twin rules and EJL-6/7 handle the repeats. Rows with the same reftramo, locality and department count as one copy.
- EJL-16: The real run is enabled only by the server env var `EJES_CALLES_REAL_RUN_ENABLED=true` (default off). With the switch off, `dryRun: false` is refused with 400 and "La carga real de ejes de calles todavía no está disponible." before any DB connection, and the writer service (`runEjesCalles`, `runEjesPersistTransaction`) throws the same message, so direct calls fail closed. One shared helper (`domain/realRunSwitch.ts`) holds the check.
- EJL-17: Renumber uniqueness. A candidate pair (a removed section and a new section of the same `idcalle` within the candidate distance, Hausdorff under `RENUMBER_HAUSDORFF_M`) is renumbered only when all three hold: its old `reftramo` names exactly one current `road_section` row; it is the only candidate of that old `reftramo`; it is the only candidate of that new `reftramo`, and that new `reftramo` has exactly one kept copy (EJL-6). Any other candidate is not renumbered. It is reported as skipped with its reason: `repeated_old_ref` (the old `reftramo` names more than one row), `ambiguous_old_ref` (the old row has more than one candidate), `ambiguous_new_ref` (the new `reftramo` has more than one candidate), `not_single_copy` (the new `reftramo` has zero or several kept copies). Its points stay on the old `reftramo`, and both sections are held as EJL-12 says. The renumbered set is decided once, in the analysis of the transaction (EJL-23), and the load writes exactly that set: the analysis count `renumbered` equals the load count.
- EJL-18: Ways for moved sections. The `circulation_way` rows of EJL-5 are built from every kept copy that is NEW or whose `idcalle` differs from its pair's current `idcalle`. A section moved to a brand-new `idcalle` therefore gets its way row, and the update sets its `id_circulation_way` to that way's `id_calle`. Existing ways are untouched.
- EJL-19: Reference normalisation. `reftramo` and `idcalle` compare as canonical text: trimmed, and when the text is an integer, without leading zeros (`'0123'` equals `'123'`, `'012'` equals `'12'`). Non-integer text is compared as text and never cast. The rule applies to the staging, to `road_section`, to `access_point.id_road_section`, to `circulation_way.id_calle`, to the twin groups, to the renumber, and to the geometry map. Written values are the canonical form. Staging rows with the same canonical `reftramo` are one repeated group, and the staging row used for classification is chosen by its full content (deterministic). A re-run over leading-zero staging changes nothing (EJL-14).
- EJL-20: Staging fingerprint. The analysis computes `staging_rows` (the row count of the staging table) and `staging_digest`: the md5 of the sorted per-row md5 values, each over `reftramo`, `idcalle`, `nombre`, `tipo_vialidad`, `fuente`, `departamento`, `localidad` and the md5 of the geometry EWKB, with NULLs distinguished. The dry-run result carries both. The real-run `summary` must carry both (missing or empty fails with 400). Inside the transaction, the analysis is checked against the summary (the counts of EJL-1 and this fingerprint): any difference aborts before the backup with "vuelva a analizar".
- EJL-21: Revert file cleanup. The revert file is written, verified and registered before the first write (EJL-4). If a later write or the ANALYZE of the changed tables fails, the transaction is rolled back and the file is unregistered and deleted, so no revert file remains registered for a rolled-back run. A failed COMMIT keeps the file, because the outcome is unknown.
- EJL-22: Real-run request. The "Cargar ahora" request is `{connection, tables, dryRun: false, accepted: {}, summary}`, where `summary` is the counts and the fingerprint of the finished dry-run result. The dry-run request stays `{connection, tables, dryRun: true}`. "Cargar ahora" still needs the analysis key (host, port, database, user and the five tables) of the finished analysis, a password typed again and no blocker.
- EJL-23: One classification per load. The real run classifies the staging once, inside the locked transaction: the analysis writes the renumbered set to the temp table `ej_renum` (a data-modifying CTE of the same statement), and the load reads that table. The kept copies per `reftramo` come from the same statement (`copy_refs`, a `GROUP BY ref` count, as EJL-17 needs them); the skipped pairs go to a second temp table, `ej_held`, whose new `reftramo` copies the load deletes before it pairs anything (EJL-12). No correlated count per row, and no second classification.
- EJL-24: Privileges before the lock. Before `LOCK`, the real run checks the write privileges each table of EJL-2 needs (`road_section`: SELECT, INSERT, UPDATE, DELETE; `circulation_way`: SELECT, INSERT; `addresses_master`: SELECT, INSERT, DELETE; `access_point`: SELECT, UPDATE; DELETE on the two tables is for the removals and merges of slice A), and one of UPDATE, DELETE or TRUNCATE on each of the four locked tables, since `SHARE ROW EXCLUSIVE` needs one of them. `ANALYZE` skipped because the user does not own a table is only a warning: the server skips it, the load goes on, and the warning is listed in `privilegeInfo` of the dry-run result and of the real-run result.
- EJL-25: The revert file name carries the milliseconds of its run after the seconds (`ejes-revert-<schema>-<table>-<yyyymmdd>-<hhmmss>-<mmm>.sql.gz`), so two real runs in the same second on the same table do not collide (`EEXIST`). The shared `BACKUP_FILE_PATTERN` (`^(padron|centros-anep|ejes)-revert-.*\.sql\.gz$`) still matches.
- EJL-26: Sections without a `reftramo` are never renumbered. A removed section whose `reftramo_ideuy` is NULL (or empty) is never a renumber candidate (EJL-17): it is neither renumbered nor held, and it stays an ordinary removed row of the splits, merges and plain removals, as before.

EJL-1 to EJL-26 (26 criteria).
