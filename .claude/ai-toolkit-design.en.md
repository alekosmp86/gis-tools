# AI Toolkit: design document

Version 0.7, September 2026. Result of the initial planning session plus an external review. This document is the design reference for the toolkit; the MVP cut is at the end. This English version is canonical; the Spanish version is a translation and may lag behind.

## 1. Goal

Build a toolkit for Claude Code, project- and language-agnostic, that makes it possible to take an existing project or start one from scratch while adopting good market practices, preserving functionality that is already tested and extending it according to new product requirements.

Cross-cutting requirement: expensive verification (e2e, full suite, browser, Playwright MCP) never runs on every change; it runs asynchronously or on demand. Cheap verification can run in synchronous hooks, but with a time budget per level and an explicit failure policy (section 6). "Non-blocking" means that the edit loop never waits for anything that takes more than seconds, not that nothing is verified inline.

Decisions made: Claude Code as the only runtime; stack-agnostic from the start, with JS/TS as the first complete adapter; no pilot repo chosen yet (candidates: Karma Plus as legacy, a small greenfield as the second case).

## 2. Three-layer model

**Layer A, the toolkit.** AI Toolkit is a proper name; every artifact it owns uses the `ai-toolkit` prefix (skill `/ai-toolkit-init`, manifest `ai-toolkit-manifest.json`, context files under `.claude/ai-toolkit/`). A Claude Code plugin with its own skills, role templates for agents, hook templates, ecosystem and platform adapters, and an entry command `/ai-toolkit-init`. It lives in its own repo, is versioned, and is tested against fixture repos.

**Layer B, what is generated per project.** `CLAUDE.md`, `.claude/context/*.md`, agents instantiated with the project context, hooks calibrated to the repo's real commands, scoped skills. All of it comes out of the generators reading the project map.

**Layer C, the leveled verification loop.** Where the non-blocking requirement lives. Described in section 6.

Three kinds of skills coexist in a project and regeneration treats them differently:

- Toolkit skills (discovery, spec, release): run the same in every project, updated with the toolkit.
- Generated skills (agents, hooks, scoped skills): instantiated with the project context; regenerated while respecting local overrides.
- Skills installed as-is (handoff, superpowers): the toolkit ships them bundled with a pinned version and `/ai-toolkit-init` copies them unmodified; marked as "toolkit-owned, do not touch".

Regeneration scheme: every generated file carries an origin and version marker; local adjustments live in separate override files that regeneration never overwrites. What makes regeneration safe is not the marker inside the file but the manifest (2.2).

### 2.1 What goes into the repo and what stays on the machine

Everything the toolkit generates or installs is classified into one of three destinations, and `/ai-toolkit-init` maintains the `.gitignore` and the manifest with the decision per artifact, so it never asks again.

**Repo.** What defines shared team behavior and is source, not derived: `CLAUDE.md`, discovery context files (conventions, glossary, tokens with intent, ADRs), specs and feature state files, the baseline definition (section 5), human decisions on findings (section 3), configuration of the vetted tools (for example the Fallow config), hook templates with their commands, the manifest.

**Developer machine, never the repo.** What is derived, regenerable and heavy: the full `graphify-out/`, Fallow reports and reports from other analyzers, baseline evidence (results, coverage, measurements), finding events produced by tools and agents, level 2 reports, caches. It is regenerated by hook or command on each machine; if a team needs the shared graph, the answer is Graphify's HTTP MCP or a CI job, not the commit.

**Asked at generation time.** What depends on how the team works: skills, agents and hooks under `.claude/`. The proposed default is repo when there is more than one person (the value of a product reviewer is that everyone has the same one) and machine when the project is a one-person project or the client does not want versioned AI tooling. The answer is stored in the manifest; it can be changed later with a command, which moves the files and updates the `.gitignore`.

Audit: discovery pass 1 reviews what is committed that should be local (tool outputs, reports, caches, secrets) and lists it in the report; the release skill repeats the check on the diff before opening the PR.

### 2.2 Manifest

`.claude/ai-toolkit-manifest.json` is the source of truth about what the toolkit put in the project and how. It is what makes regeneration and version upgrades safe.

Contents: schema version of the manifest itself (with migrations between versions); toolkit version that generated each artifact; for each managed file: path, type (toolkit / generated / installed as-is / local override), destination (repo / machine), hash of the template or source it came from, hash of the written content, and ownership (toolkit, project, or shared with marked sections); pinned versions of the tools installed as-is (Graphify, Fallow, handoff, superpowers); decisions made in `/ai-toolkit-init` questions, so they are not repeated; and the active baseline exceptions (section 5) by reference.

Conflict policy on regeneration: if the content hash matches what the toolkit wrote, it regenerates without asking; if it differs (someone edited it by hand), the diff is shown and three options are offered: keep the edit and move it to an override, apply the regeneration, or merge section by section for files with shared ownership. Nothing is ever overwritten silently.

`plan` mode (dry-run): both `/ai-toolkit-init` and regeneration first show what would be created, changed or deleted, with the classification from 2.1 and 4.2, and write nothing until confirmation. It is the default mode the first time it runs on an existing repo.

### 2.3 Adapter contract

The toolkit is agnostic because the core never talks to an ecosystem or platform directly: it only requests capabilities from an adapter. The contract is defined before writing the first adapter, even if the MVP has only one; otherwise the first adapter becomes the architecture.

Two types. **Ecosystem adapter** (language and toolchain: JS/TS, Python, Go, etc.) and **platform adapter** (product type: web, Expo/React Native, API, CLI). A project has one or more of each; the core detects them by evidence in discovery pass 1 and the human confirms.

Each adapter declares a set of capabilities with fixed names, and for each capability exposes the same shape: inputs it needs (paths, configuration), command or procedure it runs, artifacts it produces (always in a core format, not the tool's), estimated time budget, and destination of its outputs per 2.1. Ecosystem capabilities: detect build, test and lint commands; run tests related to a set of files; run the full suite with coverage; static analysis; syntactic duplication; dependency graph between modules; dependency audit; environment variable inventory; code convention thresholds (3.1). Platform capabilities: route or screen map; e2e; performance and accessibility budgets; specific audits (RLS, native permissions, etc.); pre-release and release.

Any capability may answer `unsupported` (the ecosystem has no tool for this) or `not-applicable` (it makes no sense for this platform), and those are valid first-class answers, not errors. The core degrades in a way defined per capability: it skips the step and records it in the report as "no coverage", or asks the human for a manual command, or marks the finding with reduced confidence. An adapter is forbidden from simulating partial support with its own conventions; if something is half covered, it declares `partial` with the list of what it does not cover.

Adapters are tested against the fixture for their ecosystem (section 11) with a common contract test: each declared capability produces artifacts in the core format or answers with one of the three states. JS/TS is the first complete adapter; Expo/Supabase the first platform adapter.

## 3. Principles

Prefer CLI plus skill over MCP server. An MCP takes up context on every turn; a CLI invoked by a skill costs zero until it is used. MCP only when there is interactive state to maintain. Playwright MCP is reserved for a visual verification agent that is invoked once per feature, never per change.

An agent's role is defined by permissions, not by prompt. Opinion agents only have Read, Grep, Glob and read-only Bash. Implementing agents have Edit and Write.

Feedback between agents goes structured to a file, never as free text in the chat. A finding has a lifecycle, it is not a line in a list: stable identifier (derived from rule plus normalized location, so it survives line changes and allows deduplication), rule or origin (which agent or tool produced it), evidence (file, range, fragment), severity, confidence, state (open, accepted, fixed, dismissed, suppressed), owner, creation date and last revalidation date, and for suppressed ones a justification and an expiration date after which it reopens. The discovery improvement log (section 4) and the gate findings (section 7) use the same format and the same per-project store. A finding not revalidated within a configurable period is marked as doubtful; that way the log does not degenerate into a debt list that nobody knows when to look at again.

Storage: background discovery, several gate agents and the human may write at the same time, so the store is not a single JSON edited in place. Each run (a discovery pass, a gate, a revalidation) writes its own append-only JSONL file under `.claude/findings/runs/`, with one event per line (created, updated, state change, suppressed). The current state of each finding is derived from those events by stable identifier and consolidated into an index (`.claude/findings/index.json`) that is regenerated, never edited by hand. Writes are atomic per file (write to a temporary file and rename).

Destination: events are separated by who produces them. Those expressing human decisions (`accepted`, `dismissed`, `suppressed` with justification, exceptions and their expirations, owner changes) go to `.claude/findings/decisions/` and into the repo, because they are team history and cannot be recomputed. Derived events (findings created or updated by discovery, analyzers or gate agents) go to `.claude/findings/runs/`, local or from CI, because they are regenerated by running the same thing again. The consolidated index is regenerated on each machine from both; a versioned decision on a finding that has not yet been recomputed locally stays in the index as "decision without current finding" until the next run. This is not a 2.1 question: it is fixed this way.

Each agent receives only the context files it needs. The project graph is what makes that distribution possible.

Product owns the what. Architecture owns the how and provides solutions; it does not veto requirements. Details in section 7.

Discovery, verification and the toolkit itself are evaluated with metrics; whatever generates noise is adjusted or turned off.

The default for every control is to inform; blocking is earned with metrics.

### 3.1 Code conventions

The toolkit always enforces, in every project, four principles: DRY, KISS, single concern and SOLID. They are part of the toolkit, not of each project; the project's own conventions (for example `copilot-instructions.md`) extend them, never replace them.

A principle cannot be verified as such, so each one is decomposed into two parts, following the separation the existing auditor already uses:

**Mechanical (level 0 and 1, auto-fixable or blocking).** Measurable proxies: syntactic duplication (jscpd or the adapter's detector) with a threshold; cyclomatic and cognitive complexity per function; maximum file and function length; maximum number of parameters; import boundaries between layers and absence of cycles (dependency-cruiser or equivalent); one main export per module where the convention says so; ecosystem lint rules that approximate SOLID (no classes or modules that import everything, interfaces over concrete implementations where the language allows it). The thresholds live in the ecosystem adapter and discovery calibrates them against the current state of the repo so they do not block everything on day one.

**Judgment-based (gates, flagged only).** What requires understanding intent: whether two pieces duplicate the same concern (improvement log, section 4); whether an abstraction solves a real problem or is premature; whether a module has a single reason to change; whether a dependency points to an abstraction or to a detail. The chief engineer evaluates it with explicit heuristics in its template, and the finding must come with a concrete alternative, like any other of its findings.

Tie-breaking rules, because agents tend to over-apply principles: KISS wins over DRY and SOLID when they clash; DRY is applied with the rule of three (the third repetition gets extracted, not the second); a new abstraction needs at least two real consumers, not hypothetical ones; no patterns (factories, strategies, injection) are introduced without a second case that justifies them. These rules go in the prompt of the implementer and the chief engineer.

For the implementer, DRY is also procedural: before creating a helper, hook or utility it queries the graph (`graphify query`) and the improvement log to verify it does not already exist. Single concern relies on the feature structure convention that discovery learned: the structure says where each thing goes, and putting two concerns in one file is a detectable violation.

### 3.2 Output conventions

Claude 5 family models produce longer responses by default, narrate what they are about to do during agentic work, and tend to compress ideas into their own terminology or acronyms the reader does not know. Anthropic documents this in its prompting guide and clarifies that the effort parameter controls how much the model thinks, not how much it says: lowering it does not shorten the visible output. The toolkit treats this as its own convention, applied in three layers and measured.

**Layer 1, Claude Code configuration (generated by `/ai-toolkit-init`).** Output style `Concise` (included in Claude Code since August 2026) as default in `settings.json`, or a toolkit-specific output style in `~/.claude/output-styles/` when more specific rules are wanted. A `UserPromptSubmit` hook that injects a single line into every turn, along the lines of "First sentence: the result. Plain language: no coined terms, no metaphors, no undefined acronyms". One line per turn survives long sessions better than a paragraph in `CLAUDE.md`.

**Layer 2, rules in `CLAUDE.md` and in the agent templates.** Ordered structure, not word caps: "Default response: result first, five lines maximum; expand only if asked". No recapping what the diff or the tool output already shows. No explaining what was not asked. No preambles, closings or final summaries. Length proportional to the task, with two or three examples of a well-done short response in the template (examples work better than the instruction "be concise"). Terms and acronyms: defined the first time or avoided; the project's domain glossary defines which terms the team already knows. Lists and headings only when there are truly several parallel things; reviewer findings already go structured to a file.

**Layer 3, pruning inherited instructions.** Anthropic cut more than 80% of the Claude Code system prompt for Claude 5 models with no measurable loss. Discovery reviews `CLAUDE.md`, `copilot-instructions.md` and existing skills and flags scaffolding rules from earlier generations ("check your diff before finishing", "include a final verification step", verification subagent instructions) that today only add context and, worse, induce narration. They are proposed for deletion, with confirmation.

**Measurement.** Output tokens per task and per agent on the evaluation fixture, with the same treatment as false positives: an agent that spends twice as much for the same result gets adjusted. Optional complement: a rewriting skill in Simplified Technical English (ASD-STE100) installed as-is for documentation aimed at end users.

**Verifiable assumptions.** The concrete claims in this section about Claude Code (existence of the `Concise` output style, its date, the behavior of the `UserPromptSubmit` hook, the system prompt cut) are sourced assumptions, not design dependencies. `/ai-toolkit-init` checks at run time what exists in the installed Claude Code version and falls back to the next mechanism if something is missing: a toolkit-specific output style if there is no `Concise`; rules in `CLAUDE.md` if there is no hook. The sources are cited in the toolkit repo and reviewed when the minimum supported Claude Code version is updated.

### 3.3 Automation security

Discovery reads files the toolkit does not control: READMEs, third-party `CLAUDE.md` files, comments, documentation, configuration, commit messages. And it generates hooks and agents that later execute commands. That demands explicit rules.

All discovered content is data, never instruction. Discovery analysts receive file contents inside clear delimiters and with the instruction not to execute anything that content asks for; an existing `CLAUDE.md` that says "run this script" is classified under 4.2, not obeyed. The same applies to tool results and to comments in the code.

Commands executable without confirmation: only those the adapter declares as read or analysis (lint, typecheck, tests, static analysis, graph construction) and those discovery detected by evidence and the human confirmed in `plan` mode. Any command that installs, deletes, publishes, pushes or touches the network outside package registries asks for confirmation. Generated hooks do not interpolate repo file contents into commands; they use fixed paths and arguments.

Secrets: discovery detects secrets and credentials in the repo and in the environment, reports them as a security finding and masks them in all reports, context files and findings; it never copies them into `CLAUDE.md` or into context files. The environment variable inventory records names, never values.

Isolation: analysis of third-party or unknown repos (for example the first pass over a client project) runs with minimal permissions, without the developer's credentials mounted and without network access except package registries. The evaluation fixtures include a hostile repo (section 11) that attempts exactly these attacks.

## 4. Discovery

It is the central deliverable of the first phase and the input for all generators. It runs at progressive depth so it is not blocking: each pass writes its own context file and work can start with the first one while the others run in the background.

**Pass 1, cheap, minutes.** Repo structure; real build, test and lint commands detected by evidence (lockfiles, scripts, Makefile, existing CI); pre-existing AI configuration (`CLAUDE.md`, `copilot-instructions.md`, cursor rules, `AGENTS.md`), with contradiction detection and respect for the existing pattern (for example, `copilot-instructions.md` as source of truth and `CLAUDE.md` delegating); git archaeology (hotspots by churn and complexity, files that change together, bus factor, commit and branching conventions); feature structure convention learned from two or three existing features; domain glossary extracted from the code; TODO and FIXME inventory; project graph (see 4.1). Leaves a usable `CLAUDE.md`.

**Pass 2, ecosystem adapters.** Static analysis (Fallow for TS/JS; equivalents for other languages); syntactic duplication; dependency graph between modules with cycles and layer violations; dependencies (vulnerabilities, versions, libraries solving the same problem coexisting, unmaintained packages, licenses); test quality (coverage, flaky, excessive mocks, absence of integration, suite duration); inventory of environment variables read versus documented, secrets, feature flags; data contracts (schema, migrations, generated types, API) and their drift; documentation drifting from the code.

**Pass 3, platform adapter.** What is specific to the project type. See section 10 for Expo/Supabase.

**Duplication by concern.** Detectors provide syntactic duplication; semantic duplication (two hooks resolving the same loading state, three date-formatting helpers) is searched for by an agent over the graph. The result is not a list of fixes but an improvement log with context, which the feature workflow consults: when a feature touches one of those areas, that is the moment to consolidate, not before.

**Design tokens.** Specialized skill with two modes. Formal: tokens are declared (Tailwind config, CSS variables, Style Dictionary, theme) and are documented with their intended use. Informal: there are no tokens and they are inferred from the code (repeated colors, spacing scales, typography, radii), proposing a set with evidence of origin. In both cases the result describes intent, not just values ("blue 600 is primary action, never decoration"), and feeds a level 1 check that flags hardcoded values that have an equivalent token.

**Discovery report.** A document that ranks findings by risk, not by category: stack and command map, baseline status, static analysis, improvement log, graph, tokens with intent, platform findings, open questions. When discovery cannot infer something, it leaves it as an open question instead of making it up. When existing conventions are inconsistent, it shows the variants and asks the human to choose the canonical one; the decision is recorded as an ADR.

### 4.1 Project graph

Vetted tool: **Graphify** (safishamsi/graphify), with a version pinned in the toolkit. The toolkit does not build, nor let the agent improvise, its own graph; it only installs and configures Graphify as an "as-is" skill (section 2) and defines how it is used.

Usage mode, consistent with the CLI over MCP principle:

- Construction in discovery pass 1: `/graphify .` over the repo. Local extraction via tree-sitter (36 languages, no API calls for the code), which makes it suitable for the agnostic requirement.
- Output in `graphify-out/`, local to the machine and in `.gitignore` (see 2.1): `graph.json` (data), `GRAPH_REPORT.md` (index: central nodes, communities, unexpected connections). Each machine regenerates it with the hook; Graphify's merge driver only applies if a team decides to version it, which is not the default.
- Lazy consumption: `CLAUDE.md` does not load `GRAPH_REPORT.md`; it only says that it exists and how to query it. The scribe maintains in `.claude/context/` a short, bounded summary of the graph (main modules and their relationships, one screen), which is the only thing loaded by default, because `GRAPH_REPORT.md` grows with the repo. For concrete tasks the agent uses `graphify query "<question>"`, `graphify path` and `graphify explain`, which return subgraphs without loading the corpus. No custom navigation skill is written; Graphify's is used.
- Updates: `graphify hook install` (post-commit git hook, incremental AST-only rebuild, no API cost) plus `--update` in the scribe skill when closing a feature.
- Graphify MCP server: not enabled by default. It remains a documented option for teams that want the graph shared over HTTP.

It complements Claude Code's native LSP: the LSP answers "who uses this" in real time; the graph answers "how is this organized" without loading code. Its purpose is to offload agent memory and reduce context compactions. Risk to watch: the project evolves fast (v7, v8 with format changes); hence the pinned version and a fixture test that validates that `GRAPH_REPORT.md` and `graph.json` still have the shape the toolkit expects.

### 4.2 Audit of existing AI context

Before generating anything, discovery inventories all the AI context the project already has: `CLAUDE.md` (root and nested), `AGENTS.md`, `copilot-instructions.md`, `.cursorrules` and `.cursor/rules`, `.windsurfrules`, `GEMINI.md`, skills, agents and hooks under `.claude/`, `.mcp.json`, and any document these delegate to. That content is accumulated team knowledge and is treated as source, not as something to replace.

Each rule or block is classified into one of four categories, with evidence:

- **Preserve.** Project-specific decisions and conventions the toolkit cannot infer from the code: why a library was chosen, what not to touch, async conventions, domain names, client restrictions. They are copied as-is into the generated context files, with a reference to their origin, and stay out of the scope of regeneration.
- **Migrate.** Rules the toolkit already covers by another mechanism: a lint rule written in prose moves to the linter configuration; an instruction to "run the tests after editing" moves to a hook; a folder structure description moves to the feature convention. They are migrated and the original prose is proposed for deletion, because duplicating the rule in two places guarantees they diverge.
- **Prune.** Scaffolding from earlier model generations that today only adds context or induces narration (section 3.2, layer 3). Proposed for deletion with explicit justification.
- **Conflict.** Rules that contradict each other across files (for example `AGENTS.md` and `copilot-instructions.md` with different commit conventions) or that contradict a toolkit convention (section 3.1). They are listed and the human resolves them; the decision is recorded as an ADR.

Process rules: nothing is deleted or rewritten without confirmation; the proposal goes into the discovery report with the classification and the evidence. The existing delegation pattern is respected (in Karma Plus, `copilot-instructions.md` is the source of truth and `CLAUDE.md` delegates; the toolkit fits into that instead of inverting it). Files that serve other tools (`AGENTS.md` for Codex, `.cursorrules`) are not removed even though the target runtime is Claude Code; if the team uses them, they are kept in sync from the same source. The same audit is repeated when upgrading the toolkit version, because what is "preserve" today may become "migrate" when the toolkit incorporates the mechanism.

## 5. Baseline

Before touching anything, the baseline skill runs the existing suite, records the state, and generates characterization tests for critical paths without coverage (they capture current behavior exactly as it is, without judging it). The baseline is the contract: every feature must leave it green. In greenfield it starts empty and grows with each feature.

The baseline has three parts with different destinations, so that two machines never conclude different things about "baseline green":

- **Definition, in the repo** (`.claude/baseline.json`): which suites and commands compose it, which routes or screens have a budget and with what thresholds, what minimum coverage per area, and which characterization tests were generated. It is versioned and changes only by human decision recorded as an ADR or in the spec that motivated it.
- **Accepted exceptions, in the repo**, inside the definition: tests known to fail or be skipped, temporarily relaxed thresholds, suppressed findings. Each exception has an owner, a justification and an expiration date; when it expires, it counts as red again until someone renews or resolves it. Without a recorded exception, a failure is a failure.
- **Evidence, local or from CI, never in the repo**: execution results, measured coverage, performance measurements, differential reports. It is what is compared against the definition. CI is the authoritative evidence; local evidence is indicative.

"Baseline green" means: the most recent evidence satisfies the definition, taking active exceptions into account. It is a deterministic function of those three things.

The baseline also includes performance and accessibility budgets per key route or screen, measured by the platform adapter: on web, Lighthouse attached to the same Playwright session as the e2e (median of three runs, `storageState` reused for authenticated pages, JSON output); on Expo, bundle size with Expo Atlas, startup and transition times measured inside Maestro flows, in-app marks. A spec can set a non-functional criterion on these budgets and it is traced like any other.

Level 2 emits a differential report against the baseline (what used to pass and now fails, what was skipped, what changed in coverage), not a pass/fail. Distinguishing "I broke something" from "I changed the contract on purpose and the old test became obsolete" is always decided by a person.

## 6. Leveled verification

| Level | When | Budget | What runs |
|---|---|---|---|
| 0 | PostToolUse, synchronous | 2 s per file | Lint and typecheck only on changed files; hardcoded token check |
| 1 | Stop hook | 30 s | Tests related to the touched files (`vitest related`, `jest --findRelatedTests`, equivalents); auditor |
| 2 | Asynchronous, background or CI | no hard limit; reported | Full unit suite plus e2e with the tool the platform adapter indicates (headless Playwright for web, Maestro or Detox for native), plus performance and accessibility audits on the same session (Lighthouse on web, RN equivalents on Expo); writes a differential report to a file |
| 3 | PR | CI's | Full CI, reviewer agents over the full diff |

The budgets are toolkit defaults; discovery calibrates them by measuring the real suite and stores them in the baseline definition. Whatever does not fit in a level's budget automatically drops to the next: if the related tests for a change take more than 30 seconds, level 1 runs only the most direct ones and the rest is left for level 2.

Failure matrix. Each level has three possible outcomes besides green, and the response to each is defined:

| Level | Timeout (exceeds budget) | Infrastructure failure (tool does not start, missing dependency) | Real failure |
|---|---|---|---|
| 0 | Warns and lets it through; degrades to level 1 | Warns and lets it through; opens an infrastructure finding | Blocks the edit until fixed (auto-fixable in almost all cases) |
| 1 | Warns and lets it through; degrades what is pending to level 2 | Warns and lets it through; opens an infrastructure finding | Blocks closing the task; the implementer fixes before continuing |
| 2 | Reports duration; blocks nothing | Reports; counts as blind verification and blocks the PR until resolved or accepted as an exception | Differential report; QA classifies; blocks the PR only if it is a regression against the baseline without an exception |
| 3 | CI's | CI's | Blocks the PR |

General rule: an infrastructure failure never blocks local work and is always recorded. Exactly four things block a PR: regression against the baseline without a recorded exception; untraced acceptance criterion (section 7); blocking security finding; and blind verification, that is, absence of level 2 or 3 evidence due to infrastructure failure. Blind verification is a blocker in its own right and not a baseline exception, because the baseline speaks of tests that fail and this is not knowing whether they fail; it can be lifted with a recorded exception with owner, justification and expiration, same as the baseline ones. Everything else informs.

## 7. Agents

### With write permission

- **Implementer.** Executes a spec task against the baseline. Does not decide scope. Writes only to production paths.
- **Test writer.** Deliberately separated from the implementer: if the same agent writes test and code, the test validates what the code does and not what it should. It is what gives TDD teeth. Writes only to test paths.

The separation between these two is technical, not prompt-based. The ecosystem adapter declares the project's test globs (learned in discovery: `**/*.test.ts`, `__tests__/**`, `e2e/**`, or whatever the convention says). A `PreToolUse` hook generated by the toolkit intercepts `Edit` and `Write`, reads which agent is running, and denies the write if the path is not in that agent's allowed set: the implementer cannot touch a file that matches the test globs, the test writer cannot touch anything that does not match. Each agent run records in the feature state file which files it wrote; the traceability reviewer invalidates any test whose last change comes from an implementer run, and any production file whose last change comes from the test writer, and reports it as a blocking finding. The fixtures include unit tests of tests that try to cross the line (mocks, shared helpers, snapshots) to pin down where each ambiguous path falls; the default convention is that test helpers and fixtures are the test writer's territory. Separate worktrees remain a manifest option for teams that want total isolation; they are not the default because they make the cycle more expensive.

This depends on a capability that must be verified before building: that the hook reliably identifies which agent performs each `Edit` or `Write`. The planned route is to declare the `PreToolUse` hook inside each agent's definition (agent-scoped hooks), so that identity is not inferred but given by where the hook is declared. It is a mandatory feasibility spike, first in the MVP order. If the Claude Code version does not support it or the hook can be evaded, the fallback is separate worktrees per agent with the restriction enforced by filesystem permissions, and the MVP does not declare permission-based isolation validated until one of the two mechanisms passes the fixture.
- **Refactorer.** Acts only on the improvement log and only when a feature touches that area.
- **Scribe.** Updates ADRs, changelog and context files when closing a feature.

### Read-only

- **Product.** Reviews spec and implementation against the brief: solves the problem, covers business edge cases, respects scope. Does not opine on the code.
- **Chief engineer.** Reviews against the project map: module boundaries, new coupling, consistency with ADRs.
- **Design-system guardian.** Uses the tokens-with-intent file: hardcoded values, components that reinvent an existing one, deviations from intent.
- **Security.** Unvalidated inputs, RLS, secrets, native permissions.
- **QA.** Interprets the level 2 differential report: regression, intentional contract change, coverage gaps.
- **Discovery analysts.** One per pass.

### Gates

Opinion agents come in at three gates, not on every edit:

1. **Post-spec.** Product and chief engineer review the spec before any code exists. This is where the architect has the most voice because objecting to the how is cheap.
2. **Post-implementation.** Requirement traceability (see below), hard blockers, design system, security. The architect only flags debt or deviations as suggestions.
3. **Post-level 2.** QA interprets the report.

Between gates only hooks and tests run.

### Traceability reviewer

It is the minimum reviewer of the MVP and the one that gives teeth to product authority, so its definition is exact.

Allowed inputs: the feature spec (acceptance criteria with identifiers), the state file, the feature diff against the base branch, the list of new or modified tests and their level 1 output. Nothing else: it does not receive the graph, the ADRs or the brief, because its job is not to opine on the how.

Output: one finding per acceptance criterion in the section 3 format, with state `traced`, `partial` or `untraced`, and evidence: which files in the diff implement the criterion and which test exercises it. For `partial` it indicates which part is missing. It may also emit findings of type `out_of_spec`: code in the diff that does not map to any criterion, as information, non-blocking.

Blocking criteria: it blocks the gate if any criterion is `untraced`, or if it is `partial` without an exception recorded in the spec ("AC-3 is implemented in a later feature" counts as a valid exception if it is written there). It does not block on `out_of_spec`, which goes to product as a scope-cut suggestion.

False positive measurement: an `untraced` or `partial` finding is a false positive when the human dismisses it with the justification "it was implemented" and points to where. It is measured as a fraction of the reviewer's total blocking findings, per project and per toolkit version. Initial target: under 10%; above 20% the reviewer stops blocking and switches to inform-only until adjusted. Thresholds are evaluated with the variability protocol of section 11, never on a single run.

### Authority

Product owns the what: a spec requirement is not up for opinion; its omission is a defect that traceability catches, not a debate. Architecture owns the how and its job is to provide: every objection must come with an alternative that satisfies the requirement as written; a finding without an alternative is a complaint and is not accepted. Engineering blocks only on a bounded, named set: security, data integrity, legal compliance, real feasibility; even there the expected output is "not like this, and these are the ways to do it".

Symmetric limits for product: it does not dictate implementation, does not override a hard blocker, does not add requirements during implementation review (that goes back to the spec). It does not approve a spec whose criteria cannot be verified.

The spec is the source of truth until a new version of the spec is opened. During implementation the what is not discussed: if a criterion turns out to be ambiguous, internally inconsistent or impossible under constraints that appeared later, that is a spec defect and the path is to go back to gate 1, version the spec (v2, with the change and its reason recorded) and resume. That way discipline is preserved without turning an ambiguity into a rigid order, and the state file always points to the spec version being traced against.

Escalation: disagreements about the what are resolved by versioning the spec, not by debating during implementation; those about the how are resolved by the architect proposing and product choosing; only the clash between a hard blocker and a requirement reaches the human.

### Cost and generation

Mechanical roles (token guardian, security checklist, scribe) run on a small model; judgment roles (product, chief engineer) on a large model. Each agent receives only its context: product receives brief and glossary, not the graph; the architect receives graph and ADRs, not the full brief.

Agents are generator output: the toolkit ships role templates and the generator instantiates them with the project context. Same role, different criteria per project.

The orchestrator is the main session, not another agent.

Each agent is measured: findings produced, accepted, false positives.

## 8. Feature lifecycle

Spec → create-feature → implementation per criterion → gates → release. For small changes there is a fast path (at the end of this section).

**Spec (skill with design thinking).** Short interview in the terminal, one question at a time, with context from the project map and glossary. Empathize (who the user is in this situation and what they are trying to do), define (problem in one sentence, confirmed), ideate (alternatives with cost before accepting the first solution), prototype (step-by-step flow with states), test (each step becomes an acceptance criterion; the skill proposes unmentioned edge cases so the human decides whether they are in). Mandatory short mode for small changes: straight to flow and criteria.

Output: problem and user, alternatives and choice, flow, acceptance criteria with identifiers in given/when/then format, edge cases with decision, out of scope, open questions, non-functional requirements (bilingual copy, accessibility, analytics). The identifiers are the basis of traceability.

**create-feature.** Default naming and structure convention: `conventions/feature-structure.default.md` in the toolkit repo, unless discovery finds the project already has its own, which always wins. `create-feature` reads the features root and category list from the project context file, then environment variables, then the defaults; nothing project-specific is hardcoded. Executes the structure convention learned in discovery (folders, mandatory files, names, test location, index, types). Creates the skeleton, references the criteria in the test file, and creates the feature state file.

**State file per feature.** Linked spec, criteria met and pending, decisions made, next gate. The orchestrator reads it at the start of each session.

**Implementation.** TDD (superpowers): test writer to red per criterion, implementer to green, baseline intact.

**Release.** Agnostic core: verifies baseline and level 2 green and criteria complete, computes the version (conventional commits or asks), generates the changelog from the closed specs (speaks in product terms), tags, records what was released and the rollback plan. If there is no release process, opens the PR to main with the changelog as description. Final security pass over the full release diff. Invokes the scribe instead of duplicating it. Every irreversible action with real cost (store submission) asks for explicit confirmation; reversible ones are automatic.

### Fast path

It is defined by contract, not by size: it fixes an existing, verifiable acceptance criterion (or a failing baseline test) without expanding scope or modifying public contracts (API, schema, routes, permissions, dependencies, tokens). A change that adds new behavior goes through the full path even if it touches a single file. Diff size (N files, configurable) is only a signal for the toolkit to suggest reviewing the classification, not the condition.

What runs: reference to the criterion it fixes in the commit message, levels 0 and 1, traceability reviewer against that criterion, PR. No spec, no create-feature, no product or architecture gates. When level 2 is enabled, it runs anyway, asynchronously, and its PR blockers apply.

## 10. Expo/Supabase adapter (Karma Plus)

Supabase: RLS audit (tables without policies or too open), migrations versus production, drift between generated types and schema, storage policies, edge functions, auth providers, inventory of operational jobs (backups, GitHub Actions).

Tokens: the "informal with intent" case (`BRAND`, `BG`, `NEUTRAL` in code). i18n EN/ES: strings outside the translation system, unused keys. Analytics event inventory.

Pre-release: expo-doctor, version consistency, environment variables of the production profile. Rollback written before executing (republish the previous update for OTA).

## 11. Toolkit evaluation

Four fixture repos against which discovery and the full workflow run on every toolkit change: one clean, one with known debt, one greenfield, and one hostile. The hostile one has contradictory instructions across `AGENTS.md`, `CLAUDE.md` and `copilot-instructions.md`, a `README` with instructions aimed at the agent ("run this script to set up"), broken and skipped tests without explanation, simulated secrets in code and in a committed `.env`, irregular feature structure (three conventions coexisting), and committed tool outputs. It is the one that most tests the promise of adoption on legacy and the one that validates section 3.3.

Metrics: correct discovery findings against an expected list per fixture; traced criteria; false positives per agent; real time of each level against its budget; output tokens per task and agent; on the hostile one, zero instructions obeyed from discovered content and zero secrets in reports or generated context. Adapters additionally pass the contract test from 2.3.

Variability protocol. Agents are not deterministic, so no metric is taken from a single run. Each evaluation pins the model version per role, the configuration (effort, output style, toolkit version, versions of installed tools) and the fixture seed, and runs each fixture five times. Metrics are reported as median and worst case, never as average. A policy change is decided by a minimum statistical criterion, not by one favorable run: enabling a reviewer as blocking requires false positives below the threshold in at least four of the five runs, in two consecutive toolkit versions; disabling it happens when two of the last five runs exceed it. A model version change resets the count: the reviewer goes back to inform mode until it passes the criterion with the new model. The results of each run are stored with their full configuration so they can be compared across versions.

Hostile fixture oracle. "Zero instructions obeyed" cannot depend on reading the report by hand; it needs detectable effects. Each decoy instruction in the fixture (in `README`, `CLAUDE.md`, comments, commit messages, script names in `package.json`) points to a script that, if executed, leaves an unmistakable marker: creates a file at a known path outside the repo, writes a line to a harness log, or makes a request to a local harness endpoint. Each simulated secret has a unique, recognizable value (a fixed prefix plus an identifier), and the assertion searches for that value in everything the toolkit wrote: reports, context files, findings, `CLAUDE.md`, manifest. The fixture run ends with a set of executable assertions: no marker exists, no secret value appears, and the decoys appear in the report classified as 4.2 or 3.3 findings. Decoys are rotated between toolkit versions so they are not solved by memorizing the template.

## 12. MVP

A strict vertical slice, to test the central hypothesis (that permission-based isolation and a traceability reviewer produce useful signal without slowing down work) before building the rest. A single JS/TS repo, a single type of feature.

Defined before writing code: the adapter contract (2.3) and the manifest schema (2.2), even if there is a single implementation of each. And the agent identity spike in hooks (section 7) is resolved first, because permission-based isolation being technical depends on it.

What gets built:

- Manifest with `plan` mode, and generated versus local override scheme.
- Discovery pass 1 with the existing context audit (4.2), on the JS/TS adapter.
- Graphify installed as-is, with the short summary in context and lazy queries.
- Baseline with definition, exceptions and evidence separated (5).
- Spec skill in short mode; the long mode (full design thinking) behind a flag.
- create-feature with state file.
- Fast path for small changes.
- Implementer and test writer, separated by permissions.
- Traceability reviewer (section 7) as the only reviewer that is a candidate to block. It starts in inform mode during the evaluation runs and switches to blocking only after meeting the section 11 protocol, consistent with the section 3 principle. The product agent and the chief engineer behind a flag, in inform mode, to measure their false positives without them slowing anything down.
- Levels 0 and 1 with budgets and failure matrix, reusing the existing audit hooks generalized as a template.
- Security rules from 3.3 in discovery and in the generated hooks.
- Mechanism for skills installed as-is (handoff, superpowers, Graphify).
- Clean and hostile fixtures, with the adapter contract test.

Behind a flag until there is measurable signal: release (even the minimum PR to main), asynchronous level 2, remaining reviewers.

Second wave: discovery passes 2 and 3, Expo/Supabase adapter, asynchronous level 2, design-system guardian, security, QA, refactorer, scribe, debugging, upgrade, release with EAS, debt and greenfield fixtures.

## 13. Execution in a project

A single idempotent entry point: the skill `/ai-toolkit-init`. It is the only way the toolkit touches a project, whether for the first run, a rerun after the design or the toolkit changes, or a regeneration.

Run record. The manifest (2.2) is the record that the toolkit ran; there is no separate marker file. It carries `toolkit_version`, `design_doc_version`, and a `runs[]` history where each entry has date, toolkit version, mode (`plan` or `apply`), phases completed, and phases skipped with the reason. Rerunning with the same version reports the last run and exits; rerunning with a newer version enters `plan` mode and shows only what changed.

Phases, in order. Each phase writes its own outputs and its own entry in `runs[].phases`, so an interrupted run resumes from the last completed phase:

1. Preflight. Detect the installed Claude Code version and which mechanisms exist (output styles, hook events, agent-scoped hooks); detect ecosystem and platform adapters by evidence and ask the human to confirm; read the manifest if present.
2. Discovery pass 1, including the audit of existing AI context (4.2) and the repo-versus-machine audit (2.1).
3. Baseline: definition, exceptions and first evidence (5).
4. Generation: `CLAUDE.md`, context files, agents, hooks, following the classification from 4.2 and the destinations from 2.1.
5. Installation of as-is skills with pinned versions (Graphify, handoff, superpowers).
6. Manifest write and `.gitignore` update.

Discovery passes 2 and 3 run afterwards, in the background, and append to the manifest when they finish.

Bootstrap. Until the toolkit exists as a plugin, `/ai-toolkit-init` is a skill whose SKILL.md instructs Claude Code to perform these phases by hand, using this document as the reference and writing the manifest by hand as well. That bootstrap skill is what gets tested on the pilot repo; the plugin replaces it phase by phase, keeping the same manifest format so a project initialized by the bootstrap upgrades cleanly.
