# Architecture Navigation via the Dependency Graph

Before scanning the codebase broadly for **"where is X located"**, **"how does module Y connect to
Z"**, or any general **architecture** question, consult the generated dependency graph first. Only
fall back to a repo-wide `Glob`/`Grep` sweep if the graph does not resolve the question.

## Where the graph lives

- Generated by `scripts/generate-dependency-graph.cjs` (`npm run graph`).
- Written to two identical copies: `public/dependency-graph.html` and
  `docs/architecture/dependency-graph.html`.
- The graph's data is a single embedded JSON literal inside the HTML:
  `const graphData = {...};`. **Do not read the whole HTML file into context** (it is a large,
  mostly-markup/JS bundle) — extract just that JSON, e.g. `Grep` for `const graphData = ` to find
  the line, or pipe the file through a one-off `node -e` / `grep`+`sed` snippet that slices out the
  literal before parsing.
- If the graph looks stale relative to recent `src/` changes (new files, moved files, changed
  imports not reflected), regenerate with `npm run graph` before relying on it.

## Data shape

```
analysis.summary       — repo-wide totals (file count, LOC, node/edge counts, etc.)
analysis.nodes[]        — one entry per src file:
  .id / .path           — path relative to src/, e.g. "core/spatial/FeaturePreviewCap.ts"
  .directory             — containing directory
  .type / .subType / .categoryLabel — architectural classification (route, service, hook,
                            component, worker, util, type, module, data, ...)
  .loc                   — non-blank line count
  .imports[]             — relPaths this file imports (internal only)
  .importedBy[]          — relPaths that import this file
  .externalImports[]     — npm package names imported
analysis.edges[]         — { source, target, sourceType, targetType, edgeType } per import edge
analysis.cycles[]        — detected import cycles, as arrays of relPaths
analysis.orphanNodes[]   — files with no imports and no importers
```

## How to use it

- **"Where is X?"** — search `nodes` by `id`/`path`/`label`/`categoryLabel` for the matching file
  (grep the extracted JSON, or the sliced file). That gives the exact file path. Then open **only
  that file**, and use `Grep -n` on it to find the specific symbol/line before `Read`-ing a targeted
  line range — never `Read` the whole file speculatively when a graph lookup already narrowed it to
  one file.
- **"How does module/file A connect to B?"** — use `imports`/`importedBy` on the relevant nodes, or
  `edges` filtered by `source`/`target`, instead of grepping import statements across the tree.
- **General architecture questions** ("what are the layers", "what's the biggest/most-connected
  file", "are there import cycles") — answer from `summary`, `type`/`categoryLabel` groupings,
  `cycles`, and `orphanNodes` before reaching for `docs/architecture/*.md` prose.
- The graph models **file-level import structure only** — path, category, LOC, edges. It has no
  per-symbol or per-line data. It narrows *which file*; getting to *which line* inside that file is
  still a targeted `Grep`/`Read` on that one file, not a broader scan.
